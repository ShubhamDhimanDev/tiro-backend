Building a bulk importer (Super Admin panel) to load the real tyre supplier's ~800-row WooCommerce product-export CSV into the Brand -> TyreModel -> TyreVariant catalog, mirroring the existing `FitmentImportService`/`VehicleFitmentImportController` pattern for Vehicle Fitment data. Task originally briefed 2026-09-28, survived one session interruption (backend work completed in the interrupted session with no handback delivered — recovered by checking the filesystem directly rather than trusting an absent report).

**Why:** real supplier catalog data needs to get into the system; no importer existed before this. The CSV has no reliable dedicated SKU column, inconsistent attribute-column slot positions, messy free-text "Tyre Type" values, and other gotchas — see below.

**How to apply:** use this as the reference for what's built and why, before re-deriving any of the mapping decisions from scratch.

## Mapping decisions made by backend-agent (confirmed by direct code read)

- **SKU precedence:** explicit `SKU` column -> `Product IP` attribute -> suffix of `Name` after `" - "`. Unresolvable -> hard row error, never fabricated.
- **Price:** `Sale price` if present and > 0, else `Regular price` (WooCommerce's own precedence) -> whole cents.
- **Description:** `TyreModel.description` is stored as **plain text, HTML stripped** (`strip_tags()` + `html_entity_decode()`), NOT raw HTML. Decision basis: confirmed via grep that `frontend/app/tyres/[slug]/page.tsx` renders `model.description` as plain text (`{model.description && <p>...}`), not via `dangerouslySetInnerHTML` — storing raw HTML would show literal tag soup on the storefront. Security-agent is independently re-confirming this finding as part of the review above.
- **Missing `Pattern` attribute** (mainly BUDGET private-label rows): falls back to a per-brand generic model name (`"{Brand} Generic"`, e.g. "Budget Generic"), which buckets all no-Pattern rows for that brand into one `TyreModel` with many variants — flagged as a per-row warning, not an error.
- **Tyre Type -> `TyreCategory`/`TyreType` enums:** explicit lookup tables in `CatalogImportService::CATEGORY_MAP`/`TYRE_TYPE_MAP`. Deliberate design choice: `TyreType` is only confidently mapped from Tyre Type text for UHP/semi-slick (-> performance) and EV (-> eco); the `Categories` column's mud/all/highway-terrain signal (tolerant of the source data's own "Terrian" typo) is checked FIRST for tyre_type; everything else (including ordinary PASSENGER/LIGHT TRUCK/SUV values) defaults to `highway` with a warning. This means a large share of ordinary rows on the real ~800-row file will carry a "defaulted to highway" warning — an intentional transparency tradeoff, not a bug, per the service's own docblock.
- **`run_flat`:** detected from a "runflat"/"run flat"/"run-flat" substring in either the `Categories` column or raw `Tyre Type` value; model-level, not variant-level.
- **`TyreSidewall`** (no explicit CSV column — this was a gap the original brief's schema list didn't resolve, caught and filled in during briefing): rim-diameter-followed-by-"C" in the `Size` string -> `commercial`; `load_index`/`speed_rating` ending in "XL" -> `xl`; compound `load_index` (e.g. "108/106") with no commercial/XL signal -> `reinforced`; else -> `standard`.
- **Non-numeric `Profile` value** (e.g. literal "R" in the van/LT-format size "165R13C 94/93R" — a real data-quality issue in the source CSV, since that size format has no percentage profile): treated as a hard row error with an explicit "needs supplier data cleanup" message, not a crash and not a fabricated value. This was also a gap the original brief didn't explicitly resolve, caught during briefing by reading the fixture row by row.
- **Duplicate/trashed rows:** `Published < 1` and/or a `" (Copy)"` name suffix -> informational `skipped` collection, distinct from both `errors` and `warnings`.
- **Compound unique-tuple conflicts** (`tyre_model_id, width, profile, rim_diameter, load_index, speed_rating`): resolved as **upsert-in-place** (re-running the importer against a refreshed export updates existing variants' price/ean/weight/status/sidewall) rather than skip-with-note — chosen for re-run-friendliness on a periodically-refreshed supplier export.
- **Images:** collected/deduped per resolved `TyreModel` (not per variant row), stored as raw source URLs in `TyreModel.images` JSON array — no download/re-hosting attempted (explicitly out of scope).
- **Inventory:** explicitly untouched by this importer — no `InventoryItem` rows created, since the CSV's `Stock` column is blank across the real file. Must be confirmed again in the final report so nobody assumes stock got populated.
- **Result DTO has THREE separate row-note collections** (`errors`/`warnings`/`skipped`), not just one `errors` array like the Vehicle Fitment precedent's result — the frontend page must render all three distinctly, not collapse them.
