**Headline design decision — the promo-hold-vs-booking-hold interaction** (this project's recurring "two similar hold concepts colliding" pattern, see [[gap-resolution-pattern]]):
- Promo-stock hold created inside `POST /api/v1/bookings`'s existing transaction (not cart-add, not order-creation) — `Booking` is already the durable cart.
- `PromotionRedemption` implements `HasHold` (`booking_id`, `status [held|confirmed|released]`, `hold_expires_at`, `quantity`) but is deliberately **not** registered in `config('holds.models')` — its `hold_expires_at` is always structurally equal to its parent `Booking.hold_expires_at`, so `Booking::releaseHold()` cascades to release its own `held` children instead of a second independent sweep.
- Confirmation (held→confirmed, `usage_count` increment) happens in the same webhook transaction that confirms `Booking`/`Order`, not at order-creation.
- **Critical rule**: promo-stock lock/re-check failure at confirmation time never fails checkout — the promotion just doesn't apply, booking/order still succeeds at full price.

**Other locked algorithms (implement exactly, not equally-plausible alternatives):**
- Evaluation order: compute each active eligible promotion's total discount across its full pooled matching-unit set, sort descending, greedily claim units, skip lower-total overlapping candidates unless `stackable: true`. Tie-break on lower `Promotion.id`.
- 4-for-3: pool all matching cart units (across the eligibility scope, not per-SKU), sort by unit price descending, partition into consecutive groups of 4, cheapest unit in each *complete* group is free, trailing partial group gets nothing.
- Price-guarantee claims: `auth:customer`-only, no guest path, no Idempotency-Key needed (duplicate claim = admin-queue nuisance, not a money bug). Post-purchase approval reuses Phase 4's refund flow verbatim. Pre-purchase approval applies as an additive discount line via `approved_discount_amount`/`expires_at`/`redeemed_at`, **server-side capped to never exceed the matched line's price** — required validation, not optional.
- No promo-code entry this phase (open decision #18, deliberately not escalated — auto-applied only).
- Open decision #7 (`PriceRule` = per-zone service-fee only, not full per-zone product repricing) is still genuinely unconfirmed by the client — built to the service-fee-only assumption per the architecture doc, flagged as needing a real product-owner answer before launch, not an engineering default to relitigate mid-build.

**Delegation plan (sequential, backend first):** backend-agent builds migrations/engine/endpoints/cascade/claim-workflow first (everything else depends on real endpoints existing) → super-admin-agent (Promotions admin + claim review queue) and frontend-agent (cart/checkout promo display + claim submission UI) in parallel once backend lands → security-agent on the flagged items (discount never client-input, `promotions.manage` gate actually enforced at route/policy level, `approved_discount_amount` cap is real and tested, 4-for-3/promo math can never drive `grand_total` negative — explicit concurrency test mirroring Phase 3's technician-slot test) → qa-lead final sign-off.

**Item 4b found a real, previously unflagged bug — a second, independent oversell race, distinct from the quantity-aware fix earlier in this phase.** In `BookingController::applyPromotionHolds()`, the `Cache::lock("promo-hold:{$promotion->id}")` critical section is nested *inside* the outer booking-creation `DB::transaction()`, and its `finally` releases the lock *before* that transaction commits — unlike the technician-slot lock elsewhere in the same file, which is correctly scoped (acquired before the transaction begins, released after it commits). Concrete race: two concurrent requests against the same `stock_limit`-capped promotion (different technician slots, so no slot contention) — Request A acquires the promo-lock, sums consumed quantity, inserts an uncommitted `PromotionRedemption`, releases the lock; Request B acquires the now-free lock and runs its own SUM query *before* A's transaction commits — A's insert is invisible to B under standard isolation, so B passes the same check A already consumed. Both commit; stock gets oversold. **This matches the architecture doc's own literal wording** ("inside `POST /api/v1/bookings`'s existing transaction, acquire `Cache::lock`") — a gap in the documented design itself, not an agent deviation. Severity: High per the doc's own reputational framing, though lower-probability than the already-fixed bug (needs genuine concurrent timing on the same promotion).

security-agent deliberately did not force a literal two-connection Pest test — cited this codebase's own established precedent (`BookingLockConcurrencyTest.php`/`BookingStoreTest.php` already document `RefreshDatabase`'s single wrapping transaction makes a true cross-connection race infeasible to simulate in this harness) and verified by precise code-line citation instead, consistent with how this project has handled this exact test-harness limitation before.

**Triaged as bucket-1 (routed straight to backend-agent, not escalated to project-architect)** — recommended fix is mechanical and mirrors an already-correct pattern in the same file: rescope the promo-hold `Cache::lock` to wrap the *entire* booking-creation transaction (acquire before, release in an outer `finally` after commit — or defer via `DB::afterCommit()`), same shape as the technician-slot lock two blocks above it. Sent to backend-agent (2026-09-23) with instructions to also check for a second copy of the same lock-nested-inside-transaction pattern (the earlier quantity-aware bug needed fixing in two places), add regression coverage via the same code-citation precedent, and re-run the full suite + phpstan. **Security-agent will independently re-verify the fix once it lands — not taking backend-agent's own report as sufficient to close this out**, same re-verification discipline as the quantity-aware fix and every prior phase's security fix-then-verify loop.
