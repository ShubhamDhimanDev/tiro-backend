Kicked off 2026-09-28 by direct user request: add PayPal alongside Stripe (not replacing it), switchable server-side via ENV var. project-architect ran the contract pass same day, wrote decisions into `docs/architecture/03-integrations.md` (new PayPal subsection under item 3), `02-api-contract.md` (order response shape, new `paypal-capture` endpoint, new `webhooks/paypal` endpoint, gateway-aware refund section), `01-data-model.md` (`Payment` entity additions), `06-open-decisions.md` (item 24, same "no live credentials" gap posture as Stripe's item 23).

**Locked contract (do not redesign without going back through project-architect):**
- ENV: `PAYMENT_GATEWAY` (default `stripe`) → `config('services.payment_gateway')`. Separate `PAYPAL_MODE` (default `sandbox`, controls API base URL only — orthogonal to which gateway is active) + `PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET`/`PAYPAL_WEBHOOK_ID` under `config('services.paypal')`.
- Order response (`orderPayload()`): always all three keys — `payment: { gateway, client_secret, paypal_order_id }` — nulled out per inactive gateway, discriminated by `gateway`. `PaymentIntentResult::$clientSecret` becomes nullable.
- **Non-obvious finding, beyond the original brief:** the active-gateway singleton binding is only correct for *creating new* payments. `RefundService` and any webhook/reconciliation code touching a historical `Payment` row must resolve the gateway that row actually used (`Payment.gateway` column), not whatever's currently active in config — otherwise switching `PAYMENT_GATEWAY` mid-flight silently sends refund/webhook calls to the wrong provider's API for old orders. Solved with a new `PaymentGatewayResolver` service keyed off the `Payment` row. Webhook controllers must depend on the concrete gateway class, never the generic active-gateway interface.
- Capture flow: PayPal capture is a distinct server-side step (unlike Stripe, whose confirmation is entirely client-side + webhook-notified). New endpoint `POST /api/v1/orders/{order}/paypal-capture`, idempotency-guarded, called synchronously from frontend's `onApprove`. Webhook (`PAYMENT.CAPTURE.COMPLETED`) is an eventual-consistency backstop only, not the primary path. Capture id stored in new `payments.gateway_capture_reference` column (nullable, unique); `gateway_reference` stays the PayPal *order* id throughout. Confirm-state logic extracted into one shared service callable from both the endpoint and the webhook handler — not duplicated.
- PaymentMethod enum: new `PayPal = 'paypal'` case + `fromPayPal()` resolver, resolved inline from the capture response's `payment_source` (no extra API round-trip needed, unlike Stripe's post-hoc `retrieve()`). `retrievePaymentMethod()` on `PayPalPaymentGateway` has no real PayPal equivalent — implemented to throw, documented as unreachable-by-design.
- Webhook verification: real server-to-server call to `/v1/notifications/verify-webhook-signature` (PayPal has no local HMAC option), OAuth client-credentials token cached per `expires_in`, `verification_status === "SUCCESS"` as the only pass condition. **Cache-mark-handled-only-after-success ordering is mandatory** — this project already shipped and fixed exactly this bug once for Stripe in Phase 4 (see [[phase4-cart-checkout-payments]] and `.claude/agent-memory/security-agent/feedback_webhook_cache_ordering.md`); do not let the PayPal handler repeat it.
- Backend SDK: `paypal/paypal-server-sdk` (verified current as of 2026-09-28 — v2.3.0, actively published; older `paypal-checkout-sdk`/`rest-api-sdk-php` confirmed deprecated). Frontend: `@paypal/react-paypal-js` (verified current, v10.5.1, official PayPal-maintained, direct analogue of `@stripe/react-stripe-js`).
- Known external gap, not blocking: no PayPal credentials of any kind exist anywhere in this workspace, same posture as Stripe's still-open credential gap — tracked as open-decisions item 24.

See [[phase4-cart-checkout-payments]] for the Stripe-side precedent this mirrors, and [[delegation-conventions]] for why security-agent gets routed at the webhook/refund checkpoint rather than only at sign-off.
