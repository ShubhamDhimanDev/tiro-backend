frontend-agent's storefront redesign ("Torque & Tarmac": real brand colors, pill-button/radius rework, a genuinely new `<SiteHeader>`/`<MobileNav>`/`<SiteFooter>`, `loading.tsx` skeletons on several routes, 2 real layout-bug fixes) got a **conditional** qa-lead verdict on 2026-09-28 after a live-backend full E2E pass — not unconditional, because one real bug was found that traces directly to the redesign.

**How the run was set up** (repeatable recipe): native `php artisan serve` (NOT the docker-compose `app`/`mysql` services — those stay `profiles: [staged]` per that file's own 2026-09-11 INCIDENT note) against an isolated `scripts/test-db.sh create` schema on the existing `tiro-mysql` container, `migrate:fresh --seed`, `php artisan scout:flush`+`scout:import` to resync Meilisearch to that schema (it's a single shared index across all DBs, not test-isolated — **must flush+reimport back against the real `tiro` DB afterward**, easy to forget), `npm run dev`. Full suite: `npx playwright test` from `frontend/`, 89 tests, single worker (suite's own design), ~14.5 min.

**Result: 74/89 passed. All 15 failures individually root-caused (not left as "flaky") — 3 are real, 12 are not:**

**Real, caused by the redesign:**
1. `app/tyres/[slug]/loading.tsx` (new) breaks the HTTP status for unknown PDP slugs: page correctly renders "This page could not be found" but the response is `200`, not `404` — Next.js locks in the streamed shell's status before the async `notFound()` deep in the Suspense boundary resolves. Confirmed specific to routes that got a *new* `loading.tsx` this pass: every other "unknown slug 404s" spec (blog/location/pages/brand — none of which have a `loading.tsx`) still passes. Real SEO/correctness bug, not cosmetic. **Routed to frontend-agent.**
2 & 3. The new `<SiteFooter>` (confirmed genuinely new via `git diff app/layout.tsx` — old layout had no footer) is static/non-auth-aware (always renders "Log in"/"Create account" links, multiple `<ul><li>` nav lists) and breaks two *pre-existing* E2E specs that used unscoped global selectors: `orders.spec.ts`'s `page.locator("ul > li")` (now matches ~21 footer+content items, not 2 order rows) and `registration.spec.ts`'s `getByRole('link',{name:'Log in'}).toHaveCount(0)` after login (footer still shows it regardless of session). These are test bugs (selector was never footer-safe) exposed by legitimate new product structure — **routed to frontend-tester** to scope the locators, not a redesign defect itself.

**Not redesign regressions — confirmed via targeted re-runs and source reads, not assumed:**
- 5 (`addresses.spec.ts` x3, `http.spec.ts` x2): Next.js dev-server (Turbopack) cold-compile latency on first hit to not-yet-compiled routes — one POST literally crashed with `SyntaxError: Unexpected end of JSON input` at `request.json()` because compile delay let the body stream get consumed before the handler was ready. **Confirmed via re-run against the now-warm server: all 5 pass.**
- 1 (`browse.spec.ts` latest-releases): cross-spec test-data pollution — `database/factories/BookingLineItemFactory.php`'s `'tyre_variant_id' => TyreVariant::factory()` default cascade-creates brand-new `TyreVariant`/`TyreModel`/`Brand` rows every time any spec seeds a booking line item (several specs do), polluting the shared isolated schema's catalogue and pushing `CatalogueSeeder`'s deterministic 7-model assumption off the "latest N" page. Confirmed via factory source, not inferred from symptoms alone. Pre-existing test-isolation gap.
- 5 (`vehicles/picker.spec.ts`): confirmed via reading `backend/database/seeders/VehicleSeeder.php` directly — the spec hardcodes expectations (a "Mazda 3", a non-staggered Commodore at 235/60 R16, multiple staggered candidates sharing one disambiguation group) that plain don't exist in the actual seeder (only Mazda CX-5; the only Commodore is the staggered VF SS-V). Pure spec/seeder drift, nothing to do with the frontend.
- 1 (`checkout/prefill.spec.ts`, signed-in customer case only — the guest case passed once warm): reproducibly fails across 3 separate runs (cold, warm, warm+`PHP_CLI_SERVER_WORKERS=4`) with the same "Use a saved address" select never appearing in time. Root cause: the checkout page fires ~4 concurrent API calls (`GET /api/booking/{id}`, `POST /api/cart/calculate`, `GET /api/customer/addresses`, `GET /api/customer/vehicles`) that under this dev environment each took 3-7s to resolve even with 4 PHP workers — comfortably blowing the test's fixed 5s assertion window. Genuine local-dev perf characteristic (native `php artisan serve` + Windows + sustained concurrent load), not a code defect in `checkout-flow.tsx` and not styling-related. Flagged as backlog, not a blocker.

**What was explicitly verified clean** (the redesign's highest-risk areas per the task brief): `location/serviceability.spec.ts` (4/4 — covers the suburb/postcode input layout-bug fix), `catalog/search.spec.ts` (5/5 — covers `tyre-search-form.tsx`'s new `useTransition`-wrapped `router.push`), and every desktop-viewport header/nav interaction across the whole 89-test suite. No selector anywhere broke on the new `<MobileNav>`/`<SiteHeader>` structure itself.

**Known hazard for next time**: the persistent `docker compose` `queue-worker` service (Phase 7, consumes `otp-mail`/`notifications`/`default` off the same Redis instance a local isolated-schema `php artisan serve`/OTP-drain helper also touches) was left running this round (stopping it was denied by the permission system as "Interfere With Workloads") — turned out not to cause a problem this run (all OTP specs passed), but the race is real per `docker-compose.yml`'s own "KNOWN COLLISION" note and could cause a flaky OTP-spec failure in a future run. Worth a human decision on whether to grant that stop permission for future QA passes, or move OTP-queue isolation to a dedicated non-shared Redis DB index.
