Phase 5 (Promotions & Pricing Engine) received qa-lead **unconditional** sign-off on 2026-09-23, after security-agent's review caught one genuine high-severity bug (see below) that got fixed and independently re-verified before sign-off — not a from-scratch build with no findings.

**Final independently-verified state**: backend 582 Pest tests / 580 passed / 2613 assertions / 2 pre-existing skips / 0 failures (exact match to security-agent's own number, reproduced on a fresh isolated `test-db.sh` schema, not trusted secondhand), Pint clean, phpstan 0 errors. Frontend 167/167 Vitest tests (22 files, up from Phase 4's 103/16), lint clean (2 pre-existing warnings + 2 new same-class ones), build exit 0/58 pages. Plus a genuine live Playwright re-run (fresh isolated schema, `migrate:fresh --seed`, real `artisan serve` + real `npm run dev` + real Chromium) for the two frontend specs deferred from the first verification pass — 3/3 passed. All numbers reproduced personally, not taken from any agent's report — see [[feedback_verify_dont_trust_reports]], which held up again this phase (every relayed claim checked out under independent verification, no inflation found, unlike Phase 4's one inaccuracy).

**The real bug this phase**: security-agent's review found `BookingController::applyPromotionHolds()`'s promo-stock `Cache::lock` was scoped *inside* the booking-creation `DB::transaction()` and released before commit — unlike the correctly-scoped technician-slot lock in the same file. A concurrent request could acquire the now-free lock and stock-recheck while the first request's insert was still uncommitted/invisible under REPEATABLE READ, oversell-ing `stock_limit` under real concurrent timing. Fixed by rescoping `acquirePromotionLocks()` to run before the transaction opens and release only after it returns, mirroring the technician-slot lock exactly. Verified by qa-lead via direct code read (not just trusting the report) — confirmed correct on every exit path. One residual low-severity gap accepted as debt: `acquirePromotionLocks()`'s own loop has no try/finally, so a mid-loop `Cache::lock()->get()` infra failure (e.g. real Redis outage) could orphan an already-acquired lock — narrow, self-healing via the lock's TTL, fourth touch on this function this phase, diminishing returns to fix further.

**The permission-cache red herring, worth remembering the shape of**: backend-tester hit a real, reproducible false-403 (`ecommerce` role genuinely held `promotions.manage` in the DB but got denied) while running live Playwright against the dev server, root-caused it to `RolesAndPermissionsSeeder`'s `WithoutModelEvents` suppressing Spatie's cache-invalidation Eloquent-event path, and fixed it with an explicit `permission:cache-reset` call. backend-agent then investigated deeper (read the installed spatie/laravel-permission v8.3.0 source directly) and found the seeder's `syncPermissions()` already calls `forgetCachedPermissions()` directly, not through the event path backend-tester assumed — an empirical red/green repro with the new fix line removed still passed. So the original diagnosis's *mechanism* was likely wrong, even though the *symptom* and *fix* were both real. backend-tester's own detailed repro facts (Redis-backed dev cache, survived a full server restart, only cleared by explicit reset, its own actions ruled out as the trigger) then let qa-lead close this out with one clean, high-value check: comparing `.env.testing` (`CACHE_STORE=array`) against `.env` (`CACHE_STORE=redis`) definitively proved the Pest suite itself was never at risk regardless of the undiscovered exact trigger, since `array` cache can't leak across test runs. **Lesson**: when a diagnosis and a fix both look reasonable but a deeper investigation casts doubt on the *mechanism*, don't just accept "the fix works, ship it" or spin up a full re-investigation either — get the original discoverer's raw facts and look for one cheap, decisive check (here: a two-line config diff) that resolves the *actually load-bearing* question (does this risk test correctness / production) without needing to ever pin down the unreconstructable original trigger.

**Known backlog, deliberately NOT blocking this sign-off** (tracked here so it isn't silently forgotten or re-discovered from scratch):
1. No pagination controls on the price-guarantee claims list UI yet (frontend-agent's own flagged scope note, not a defect).
2. Post-purchase claim entry-point labels fall back to "Tyre variant #{id}" — pre-existing Phase 4 `OrderLineItem`-carries-no-tyre-name limitation, not new to Phase 5.
3. `acquirePromotionLocks()`'s lock-orphan-on-infra-failure edge case, described above — self-healing, narrow, debt not defect.
4. Permission-cache: resolved as a non-issue for test correctness; one still-open suggestion (not yet actioned as of sign-off) — a devops-agent runbook line about confirming Redis permission-cache invalidation after future permission-adding `RolesAndPermissionsSeeder` reseeds against a Redis-backed environment (production included, since Redis is "load-bearing from Phase 3" per the architecture notes).
5. **Docker Desktop reliability**: died entirely (not just a container restart) twice in this phase under normal local dev/test usage — once during frontend-tester's dispatch (self-recovered, no data loss, volume-backed), once during qa-lead's own final verification pass (same recovery: relaunch Docker Desktop, `docker start tiro-mysql` since it doesn't auto-restart even though the compose-managed containers do). Worth devops-agent's attention as a standing local-dev-environment item, not urgent, not Phase-5-specific.

**Standing condition carried forward, not new**: price-guarantee claim approval (`PriceGuaranteeClaimController::approve()`) reuses Phase 4's `RefundService` verbatim for post-purchase claims — still only verified against `FakePaymentGateway`/Stripe's real API rejecting the placeholder key, never live Stripe test-mode keys. Same condition as [[project_phase4_signoff_outcome]], not re-verified this phase, just noted as still-open dependency.

**Process note**: this phase involved an unusually long multi-round coordination chain with project-manager (multiple mid-flight findings: super-admin-agent's admin build, the audit-log double-logging question — resolved as a non-issue on both controllers, the permission-cache investigation above, and the lock bug/fix/re-verify loop) before reaching a stable state to sign off. Every relayed claim from every hop was independently checked before being accepted — none were fabricated, one (the permission-cache mechanism) turned out to be a plausible-but-wrong diagnosis that still produced a correct fix, which is a different and subtler failure mode than Phase 4's flat inaccuracy. Worth remembering that "the fix works" and "the diagnosis is right" are separately-checkable claims.
