---
name: lock-scope-vs-transaction-commit
description: Standing check for this codebase - a Cache::lock() protecting a DB write inside a DB::transaction() must not be released until that transaction has committed, or two concurrent requests can both pass the same check before either's write is visible.
metadata:
  type: feedback
---

Found in Phase 5's `BookingController::applyPromotionHolds()` (see [[project_phase5_promotions_pricing_review]]): the promo-stock `Cache::lock("promo-hold:{$promotion->id}", ...)` critical section (read consumed quantity, conditionally insert `PromotionRedemption`) is nested *inside* the same `DB::transaction()` that creates the booking, and releases via `finally` before that transaction commits.

**Why this is a real race, not just a style nit:** `Cache::lock()` is an app-level mutex, independent of the DB transaction it happens to be nested inside. Its only actual guarantee is "only one holder of this key at a time" — it says nothing about *when the effects of holding it become visible to the next holder*. If the lock is released before the DB write it protected has committed, a second, genuinely concurrent request can acquire the same lock and run its own read *before* the first request's write is durable/visible on its own separate connection — even though the second request correctly "waited its turn" for the lock, it doesn't see what the first request already wrote. Two requests can then both pass the same `consumed + requested <= limit` check.

**The codebase already has the correct pattern right next to the wrong one, in the same file:** `BookingController::store()`'s outer technician-slot `Cache::lock()` is acquired *before* `DB::transaction()` begins and released in an outer `finally` *after* the transaction call has returned (i.e. after commit) — that's why the technician-slot mechanism doesn't have this race and the promo-stock one does. When reviewing any future lock+transaction combination in this codebase, that's the reference implementation to compare against, not just "is there a lock at all."

**How to apply:** whenever a `Cache::lock()` in this codebase protects a check-then-write against a DB row (or aggregate/SUM over DB rows), trace exactly where the lock is acquired and released relative to the enclosing `DB::transaction()` call's *return* (= commit point), not just relative to the write statement itself. If the lock's `finally`/release sits inside the transaction closure rather than wrapping the whole `DB::transaction()` call, that's the same class of bug as this one, regardless of which entity/table is involved.

**Testing this class of bug:** a literal two-connection reproduction is infeasible under this project's `RefreshDatabase`-per-test harness (see `BookingLockConcurrencyTest.php`/`BookingStoreTest.php`'s own documented reasoning — the whole test lives inside one wrapping transaction, so a second real connection can't see even the test's own fixtures, let alone diverge on one row's commit visibility). Flag by code inspection with precise line citations instead of forcing a fragile test; this is a deliberate, evidence-based call this project has already made elsewhere, not a shortcut.

**2026-09-23 — fixed and re-verified for the promo-stock case (see [[project_phase5_promotions_pricing_review]]).** backend-agent's fix: hoist the lock acquisition out to wrap the whole `DB::transaction()` call (mirroring the technician-slot lock exactly) rather than nesting acquire/release inside it. When re-verifying a fix of this class, trace *every* exit path out of the locked section (normal return, each specific caught-exception recovery path, and the general uncaught-exception path) and confirm the lock-release `finally` sits at a scope that all of them pass through *after* `DB::transaction()` has already returned — not just the happy path. Also check whether the lock-*acquisition* step itself (if it loops over multiple locks, e.g. multiple stock-limited promotions in one request) has its own exception safety — a batch-acquire loop with no per-iteration try/finally can strand an already-acquired earlier lock if a later iteration's acquire throws (narrower than the original bug, TTL-self-healing, but worth a debt note, not a blocker).
