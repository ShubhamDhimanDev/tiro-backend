`App\Http\Middleware\Idempotency` (see [[project_phase4_commerce_review]]) was written for the JSON API consumer (`POST /api/v1/bookings`, `POST /api/v1/orders` — Next.js over Sanctum) and, on a missing/malformed `Idempotency-Key` header, always returns `response()->json([...], 422)` with no `X-Inertia` header. Phase 4's admin refund route (`POST /admin/orders/{order}/refund`, Inertia/session-auth) reuses this middleware verbatim.

**Why this matters:** Inertia's client protocol only parses a response as a normal Inertia visit (and threads `errors` into page props the way `assertSessionHasErrors`-style validation failures do) if the response carries `X-Inertia: true`. A response missing that header is treated as a "non-Inertia response" — in dev this surfaces as Inertia's raw error-modal dump of the response body, not an inline form error; production behavior is not a clean inline validation message either. So a raw JSON 422 hit via `router.post()`/`useForm().post()` on an Inertia route will not degrade the way a normal `ValidationException`-triggered redirect-back-with-flashed-errors would. Confirmed via reading Inertia's response-handling contract, not observed against real frontend code (the admin refund UI doesn't exist yet as of 2026-09-22).

**Two distinct things worth keeping straight when this comes up again:**
1. This is a UX/correctness gap, not a security bypass — the request is still hard-rejected before the controller/service/Stripe are ever reached either way, so no double-refund is possible even if the error never renders cleanly.
2. Separately and more importantly for actual money-safety: the whole idempotency protection only works if the client generates the UUID **once per refund-intent** and reuses it across retries of that same click/submit — not a fresh UUID per HTTP attempt. If a future frontend implementation regenerates the key on every submit (e.g. inline `crypto.randomUUID()` at click-time rather than at dialog-open/intent-start time), the backend fix is defeated identically to the original bug, just moved up a layer. This needs to be an explicit ask to whichever agent builds the UI, not just "handle the JSON error shape."

**How to apply:** recommended real fix (raised to backend-agent, not applied yet as of 2026-09-22) is a small surgical branch inside the middleware (or a thin wrapper used only on Inertia routes) on `$request->header('X-Inertia')` — return `back()->withErrors([...])` for Inertia requests, keep the raw JSON 422 for token-based API routes. Check whether this landed before assuming the mismatch is still open on any future re-review of this route or any other Inertia admin route that adopts this middleware.

**2026-09-22 update — both items now closed, verified:**
1. The `X-Inertia` branch landed in `App\Http\Middleware\Idempotency::handle()` exactly as recommended: `back()->withErrors(['idempotency_key' => $message])` for Inertia requests, raw JSON 422 unchanged for token API routes.
2. `super-admin-agent` built `RefundDialog` in `resources/js/pages/orders/show.tsx` correctly on the "mint once per intent" model this memory called for: `useRef<string>` holding the key, regenerated inside a `useEffect` keyed only on the dialog's `open` boolean (not on order id or anything else that could re-fire mid-session), `submit()` reads `idempotencyKeyRef.current` and never calls `crypto.randomUUID()` inline. Verified the specific edge case this memory worried about — a validation-error retry within the same open dialog session (e.g. amount-exceeds-balance) — does *not* regenerate the key, because `onSuccess` is the only thing that closes the dialog (`setOpen(false)`); a failed submit leaves `open` true, so the effect doesn't re-fire and the retry reuses the same key. Backend-side, `RefundService::refund()`'s pre-check-by-`(order_id, idempotency_key)` only ever matches a *persisted* `Payment` row, and a balance-validation failure throws before any `Payment` is created or Stripe is called — so reusing the same key across a "fix the amount and resubmit" retry is safe and intended, not a collision risk. Full verdict in [[project_phase4_commerce_review]].
