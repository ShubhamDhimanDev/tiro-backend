Reviewed `backend/` Phase 5 commerce build (`Promotion`/`PromotionEligibility`/`PromotionRedemption`/`PriceGuaranteeClaim`/`PriceRule`, the evaluation engine, 4-for-3 mechanics, promo-stock holds via `HasHold`, price-guarantee claim workflow, `cart/calculate` extension) on 2026-09-22, against the four items the task breakdown flagged upfront.

**Item 1 — no discount ever accepted as client input: clear.** Checked every request body touching pricing (`CartCalculateRequest`, `StoreBookingRequest`/`StoreOrderRequest` — no discount/promo field exists in either at all, confirmed via grep across `app/Http/Requests`, `StorePriceGuaranteeClaimRequest` — only `competitor_price`/`competitor_url`/`tyre_variant_id`/`order_id`, no discount field). `approved_discount_amount` is admin-only (`ApprovePriceGuaranteeClaimRequest`, gated `promotions.manage`). `PricingService::priceItems()`/`priceBooking()` is the single server-side compute path both `cart/calculate` and `OrderController::store()`'s mandatory recompute share — never trusts a client-sent amount.

**Item 2 — `promotions.manage` gating is real, not just RBAC-matrix-seeded: clear, but found (and the gap has since been closed) a real test-coverage hole.** `PromotionController`/`PromotionEligibilityController`/`PriceRuleController`/`PriceGuaranteeClaimController` all have route-level `permission:promotions.manage` middleware (`routes/admin.php`) *and* FormRequest-level `authorize()` checks calling `AdminGuard::optionalUser($this)?->can('promotions.manage')` — defense in depth, not UI-only hiding. `PriceRuleControllerTest.php`/`PriceGuaranteeClaimControllerTest.php` already had real 403 tests against `customer_support`/`operations` sessions. **`PromotionController`/`PromotionEligibilityController` had zero test coverage of any kind** when I checked (confirmed via grep across `tests/`, not assumed) — I wrote a temporary verification test hitting these routes directly with `customer_support`/`operations` sessions (all 403'd, confirming the boundary holds), then deleted it. A permanent `PromotionControllerTest.php` (12 tests, covering positive-path/audit-log/validation *and* the 403 boundary) appeared in the repo during this same review session — independently re-ran it (`--filter=PromotionControllerTest`, 12/12 passed) rather than trusting it was correct just because it existed. This closes the gap.

**Item 3 — `approved_discount_amount`'s server-side cap: clear, real, and tested both directions.** `ApprovePriceGuaranteeClaimRequest::after()` caps at `OrderLineItem.unit_price × quantity` for post-purchase claims, `TyreVariant.base_price` for pre-purchase (documented, reasonable interpretation gap — no server-side `Cart` entity exists pre-purchase to check a real line against). Existing tests cover both reject-if-exceeds-cap paths. Checked the "race between reading the line price and writing the approval" angle explicitly: `RefundService::refund()` (the actual money-movement layer the post-purchase approval calls into) independently validates against the order's *actual remaining refundable balance* (`chargePayment->amount - refundedSoFar`), so even a hypothetical bypass of the FormRequest-level cap couldn't move more money than was genuinely paid — two independent layers, not one.

**Item 4a — negative `grand_total`: clear, verified with a new end-to-end test for the exact flagged edge case.** `PromotionEvaluationService::buildResult()` clamps cumulative discount per-unit within the `Promotion` mutual-exclusivity/stacking pool. Separately, `PricingService::priceItems()` clamps the *additive* price-guarantee claim discount to `max(0, lineValue - promoDiscount)` — so a claim stacking on top of an already-maximal promotion discount on the same line (the specific scenario the task breakdown called out, since claims are deliberately outside the `Promotion` pool's own clamp) still can't go negative. No existing test proved this specific combination end-to-end, so I added one to `tests/Feature/Api/V1/Cart/CartCalculateTest.php` ("a price-guarantee claim stacking on top of an already-maximal promotion discount never drives the line or grand_total negative" — 100%-off promotion + a $50 claim on a $200 line, asserts `discount_total === 20000` not `25000`, `grand_total === 0`) — ran it standalone (passed) and as part of the full suite.

**Item 4b — promo-stock cannot oversell under concurrency: found a genuine, previously-unflagged race, distinct from the already-fixed boolean-vs-quantity bug.** See [[feedback_lock_scope_vs_transaction_commit]] for the general standing rule this establishes. Short version: `BookingController::applyPromotionHolds()`'s `Cache::lock("promo-hold:{$promotion->id}", ...)` critical section (SUM query + conditional `PromotionRedemption::create()`) is nested *inside* the same `DB::transaction()` that creates the booking, and its `finally { $lock->release(); }` fires before that transaction commits — unlike the technician-slot lock in the same file (`store()`'s outer `$lock`), which correctly wraps the *entire* `DB::transaction()` call and only releases in an outer `finally` after the transaction has already committed. Two genuinely concurrent requests targeting *different* technician slots (so no technician-slot lock contention at all) but the *same* stock-limited promotion can each acquire the promo-hold lock in sequence while the other's write is still uncommitted, both read the same (stale) `consumed` total, and both pass the `consumed + requestedQuantity <= stock_limit` check — oversells `stock_limit` by up to the sum of both requests' quantities. This isn't a backend-agent deviation from spec — `docs/architecture/05-promotions-pricing.md`'s own "Mechanism" section literally specifies "Inside `POST /api/v1/bookings`'s existing transaction ... acquire `Cache::lock(...)`", so the race is baked into the documented design, not just the implementation.

Could not write a literal passing/failing automated regression test for this specific timing race — same infeasibility this codebase's own `BookingLockConcurrencyTest.php`/`BookingStoreTest.php` already document and worked around (RefreshDatabase wraps the entire Pest test in one DB transaction, so a second literal connection can't see *any* of the test's fixture data, let alone diverge on visibility of one uncommitted row — this isn't a shortcut I took, it's the same evidence-based call the team already made for the technician-slot race). Verified by code inspection only, high confidence: traced every relevant line, confirmed no `lockForUpdate()` anywhere in the promo-redemption read path that could substitute for correct lock scoping.

**Severity judgment:** High (stock-integrity/reputational, exactly the risk class the design doc itself uses to justify `stock_limit`'s existence) but narrower-probability than the already-fixed bug — needs genuine concurrent timing on the *same* promotion (not triggered by every multi-quantity request the way the boolean-check bug was). Recommended fix direction given to backend-agent (not applied — flagged, not silently patched): rescope the promo-hold `Cache::lock()` to wrap the *entire* booking-creation `DB::transaction()` call (acquire before, release in an outer `finally` after commit), mirroring exactly how the technician-slot lock is already scoped two blocks above it in the same file — or defer release via `DB::afterCommit()`.

**Verification, not trust:** `composer audit` clean, `vendor/bin/phpstan analyse` 0 errors, `vendor/bin/pint --test`/`--dirty` passed, full suite `php artisan test --compact` (via `scripts/test-db.sh run --`, `tiro-mysql` container confirmed up first) → 580 tests / 578 passed / 2 pre-existing skips / 0 failed / 2608 assertions (567 baseline + 12 new permanent `PromotionControllerTest` + 1 new `CartCalculateTest` negative-total test).

**Verdict (initial):** needs one fix before full sign-off (item 4b, the promo-hold lock/transaction-commit ordering) — everything else (items 1, 2, 3, 4a) is clear and independently verified, not just trusted from backend-agent's self-report.

**2026-09-23 re-review — item 4b fix independently verified, closed.** backend-agent restructured `BookingController::store()`: promotion evaluation now runs once before the technician-candidate loop (cart-content-dependent only, doesn't need to be per-candidate); a new `acquirePromotionLocks()` acquires every stock-limited promo lock *before* `DB::transaction()` opens; `applyPromotionHolds()` no longer owns lock lifecycle, only the quantity-aware re-check+insert; locks release in a `finally` nested inside the outer technician-lock's `try`, only after the transaction returns (commits) — exactly mirroring the technician-slot lock's own already-correct scoping two blocks above it in the same method.

Verified by full control-flow trace (not just reading the happy path), every exit path from the technician-candidate loop iteration once `acquirePromotionLocks()` has run: normal success return, the `UniqueConstraintViolationException` replay-recovery return, and any other exception propagating out — all correctly hit the promo-lock-release `finally` before the outer technician-lock-release `finally`, and in every case release happens strictly after `DB::transaction()` has already returned/committed (confirmed there's nothing but a blank line between the lock-acquire assignment and the `try` that guarantees its release, so no gap exists there either).

**One new low-severity, self-healing edge case found and flagged (not a blocker):** `acquirePromotionLocks()`'s own internal loop (iterating multiple stock-limited promotions matched by one booking) has no try/finally of its own — if `Cache::lock(...)->get()` *throws* (rather than returning `false`) partway through, e.g. a real Redis-backed lock driver hitting a connection error on the 2nd promotion after successfully acquiring the 1st, that already-acquired 1st lock is never captured in the returned array and never released by the caller (whose `$promotionLocks` variable never even gets assigned in that case). This is a narrower failure mode than the original code had (original had a per-promotion try/finally inside `applyPromotionHolds()`'s loop, so one promotion's lock-acquisition exception couldn't strand an earlier promotion's already-acquired lock). Self-healing via the lock's 10-second TTL either way, and only reachable under actual cache-backend infra failure mid-request on a multi-promotion booking — flagged as trackable debt to backend-agent, not blocking.

Also spot-checked backend-agent's claim that `DispatchBoardController::move()` is the only other `Cache::lock()`+`DB::transaction()` pairing in the app and was already correctly scoped — confirmed directly: lock acquired before the technician-slot check, `DB::transaction()` called inside that same `try`, released only in the `finally` after. No changes needed there.

Independently re-ran (not trusted from the report): full suite via `scripts/test-db.sh run -- php artisan test --compact` → 582 tests / 580 passed / 2 pre-existing skips / 2613 assertions (exact match to backend-agent's reported numbers), `vendor/bin/pint --test` passed, `vendor/bin/phpstan analyse` 0 errors.

**Final verdict: Phase 5 is closed from a security standpoint.** All four flagged items (1, 2, 3, 4a) plus the 4b race are verified fixed with independent re-derivation, not just trust of self-reports.
