Reviewed `backend/` Phase 4 commerce build (Order/Payment/Address models, Stripe checkout + webhook, admin refund flow) on 2026-09-22, before super-admin-agent/frontend-agent build UI on top and before qa-lead's testers write coverage.

**Must-fix found:** `App\Http\Controllers\Api\V1\Webhooks\StripeWebhookController::handle()` sets the `Cache::add("stripe-webhook-event:{id}", ...)` dedup key *before* running the event handler (`match ($event->type) { ... }`), with no try/catch around it. Any exception thrown while processing (e.g. `PaymentMethod::fromStripe()`'s `default => throw` on an unmapped Stripe payment-method type — a realistic case since `createPaymentIntent()` sets `automatic_payment_methods.enabled = true`) permanently poisons that `event.id` for 24h: Stripe redelivers on the resulting 500, but the redelivery hits the cache short-circuit and returns 200 *without ever reprocessing* — payment stuck `pending`, order stuck `pending_payment`, booking never confirmed, customer already charged on Stripe's side. Existing test (`StripeWebhookTest.php`, "surfaces an unrecognized Stripe payment method type loudly") asserts the 500 as correct but never tests the redelivery-after-failure path, so the gap wasn't caught. Fix direction given to backend-agent: don't mark an event "handled" in cache until processing actually succeeds (move `Cache::add` after the match completes, or wrap in try/catch and `Cache::forget` on failure before rethrowing) — the DB-state backstop already documented in 02-api-contract.md is the right permanent source of truth, the cache should only be a fast-path, not a poison pill.

**Refund double-click verdict given (explicit ask from the requesting agent):** UI-side submit-disable is **not sufficient alone** — verdict was a real contract change is needed: a client-supplied `Idempotency-Key` on `POST /admin/orders/{order}/refund`, same as the `bookings`/`orders` creation endpoints, replacing the server-generated-per-request UUID. Reasoning: the balance-validation check only reliably catches a double-click when the doubled amount would *exceed the total charge* — for a partial refund where 2x the intended amount still fits under the charge total, Stripe's own API has no way to know the "intended single click" and will process both as legitimate separate refunds (this is the common case, not the edge case, since full refunds are naturally caught by Stripe rejecting an already-fully-refunded charge on the second call). No existing DB uniqueness constraint would catch this either, since each refund gets a fresh server-generated idempotency key/gateway_reference.

**Everything else reviewed passed:** signature verification is mandatory on every path (fails 400, no PII/secret in logs), `Order.guest_token_hash`/`order_token` faithfully reuses `Booking.manage_token`'s pattern (see [[feedback_guest_token_pattern]]), `orders.refund` permission is correctly gated at route level (not `orders.manage`), server always recomputes pricing (no client-supplied amount ever reaches `createPaymentIntent`), `GET /api/v1/orders/{order}` doesn't leak PII to token-holders, `composer audit` clean.

Lower-severity/debt items flagged: `Payment.raw_response` (full Stripe object JSON) has no `#[Hidden]` and no redaction — fine today (nothing serializes `Payment` directly yet), but flagged for whoever builds the admin Orders detail screen to exclude/redact it rather than dumping the full Stripe payload to any role that can see order detail. Guest-checkout create-or-match-by-email (an unverified guest can attach an order to an already-registered `Customer` row by supplying their email) is pre-existing, deliberate, documented design (08-customer-auth-otp.md §10), not a Phase 4-introduced gap — noted but not re-litigated.

**2026-09-22 re-review: both must-fix items independently verified closed.** backend-agent's self-report matched reality on both counts:
- Webhook fix: `StripeWebhookController::handle()` now calls `Cache::put(eventCacheKey, ...)` only *after* the `match($event->type)` dispatch completes without throwing (previously `Cache::add` ran before dispatch); no try/catch swallows the failure, so a genuine throw (e.g. `PaymentMethod::fromStripe()`'s `default => throw`) still propagates to a 500 with the cache key left unset. New test (`StripeWebhookTest.php`, "does not poison the cache dedup key on a throwing delivery...") is genuinely behavioral: first delivery throws (500, cache key unset, payment still pending), gateway double is reconfigured to no longer throw, then the *identical* event is redelivered and asserted to actually reprocess (200, payment → Succeeded, cache key now set) — not a superficial re-assertion of the original single-delivery throw test. Confirmed this covers all three handled event types since they share one dispatch/Cache::put call site, not three separate ones.
- Refund fix: `RefundService::refund()` now takes a required `string $idempotencyKey` param (no server-generated fallback), looks up an existing `Payment` by `(order_id, idempotency_key)` before ever calling Stripe, and passes that *same* key through to `StripePaymentGateway::createRefund()` as Stripe's own `idempotency_key` request option (verified in `app/Services/Payments/StripePaymentGateway.php`). Admin route (`routes/admin.php`) reuses the existing `App\Http\Middleware\Idempotency` (format-validation-only, 422 on missing/malformed UUID) verbatim. New test (`OrderRefundControllerTest.php`, "processes exactly one refund when the same Idempotency-Key is replayed") is a real integration test: two actual HTTP POSTs through the route with `actingAs`, identical header, asserting `$gateway->createdRefunds` count === 1 and `Payment` row count === 1 (not just a 200).
- Verified independently, not trusted from the report: full suite `php artisan test --compact` → 483 total/481 passed/2 skipped/0 failed (matches claim exactly), `vendor/bin/phpstan analyse` → 0 errors, `vendor/bin/pint --test` → passed, `composer audit` → clean.
- Minor doc-drift (not a security issue, flagged to backend-agent for consistency): `App\Contracts\Payments\PaymentGateway::createRefund()`'s docblock still says `$idempotencyKey` is "a server-generated UUID, reused only on a genuine retry of the same admin action" — stale now that it's client-supplied; worth a one-line docblock update so a future reader of the interface alone doesn't get the wrong mental model.
- Verdict: Phase 4 commerce backend is closed from a security standpoint. See [[feedback_idempotency_middleware_inertia_mismatch]] for the one open item (routed to super-admin-agent/backend-agent, not blocking).

**2026-09-22, frontend follow-up review — closed, sound.** Reviewed `RefundDialog` in `resources/js/pages/orders/show.tsx` (the piece that generates/supplies the `Idempotency-Key` header super-admin-agent built on top of the fixed backend contract). Verified, not just trusted:
- Key lives in `useRef<string>`, regenerated inside `useEffect` with dependency array `[open]` only (confirmed via reading the actual array, not the docstring above it).
- Traced the one path that could plausibly regenerate the key mid-retry — a validation failure (e.g. amount exceeds balance) inside the same dialog session — and confirmed it can't: `onSuccess: () => setOpen(false)` is the only thing that flips `open` to false, so a failed submit leaves the dialog open, the effect doesn't re-fire, and the retry reuses the same UUID. Cross-checked backend side too: `RefundService::refund()`'s dedup pre-check only matches a *persisted* `Payment` row, and a balance-validation throw happens before any `Payment` row is written or Stripe is called, so a "fix the amount, resubmit with the same key" retry correctly reaches Stripe fresh rather than colliding with a phantom dedup match.
- No exploitable mount/open timing gap: `useRef(crypto.randomUUID())`'s initializer gives the ref a real (if soon-discarded) UUID from first render, so it's never empty/undefined even in the gap before the `open`-effect fires; `DialogContent`'s Confirm button doesn't exist in the DOM until `open` is true, and by then the same render's passive effect has already run in practice (React flushes passive effects well before human/click timescales) — theoretical, not practically exploitable, and even if it were, the fallback is a stale-but-still-valid unused UUID, not empty/reused-and-consumed.
- Header confirmed exact-case match: frontend sends `headers: { 'Idempotency-Key': ... }`, backend's `Idempotency` middleware reads `$request->header('Idempotency-Key')` — same casing, same header, not a body field.
- `disabled={form.processing}` confirmed present; traced the theoretical rapid-double-click-before-rerender race and confirmed it's a non-issue even if it occurred, because both calls in that race would read the *same* `idempotencyKeyRef.current` (no effect refires within a click) — the actual guarantee is the reused key + backend dedup/DB-unique-constraint fallback, exactly as the component's own docstring says the disabled attribute is "not the actual guarantee."
- `form.errors.idempotency_key` cast/read matches the middleware's `withErrors(['idempotency_key' => ...])` field name exactly.
- No `<form>` element wraps the dialog inputs (button uses `onClick`, not `type="submit"`), so there's no Enter-key-triggered submit path that bypasses the same code.
- Verdict: implementation matches super-admin-agent's self-report in every particular checked; the money-safety guarantee (reuse-key-per-intent) holds at the frontend layer as well as the backend layer. This was the last open item on the refund idempotency mechanism — clear to move to qa-lead for test coverage/sign-off.
